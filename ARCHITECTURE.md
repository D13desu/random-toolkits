# Architecture and maintenance guide

This document explains how Random Toolkits is assembled, tested, and published. It is written for a maintainer who wants to add a script, menu tool, Event Log shortcut, or registry tweak without having to rediscover the build.

The project borrows the useful "editable parts are assembled into a self-contained PowerShell file" idea described in [WinUtil's architecture guide](https://winutil.christitus.com/code-reference/architecture/), but this repository is smaller and does not use WPF or JSON feature definitions.

## The five-minute mental model

```text
Editable Windows modules ─┐
                          ├─ tests/Sync-WindowsToolkit.ps1
Windows-Toolkit.ps1 ──────┤       │
                          │       └─ win/index.html
Disk-Usage.ps1 + C# ──────┘          (raw PowerShell web endpoint)

M365-Toolkit.ps1 ── hash ──> Launch-M365.ps1 ──> m365/index.html

push / pull request
        │
        └─ GitHub Actions: sync → CI-safe tests → upload artifact
                                      │
                                      └─ main only: deploy to GitHub Pages
```

- `win/Windows-Toolkit.ps1` is the Windows entry point and assembled release file.
- Some sections of that file are generated from `win/modules/*.ps1`; other sections are maintained directly in the entry point.
- `win/index.html` is not HTML. It is a byte-for-byte PowerShell copy served by GitHub Pages so `irm https://tools.d0xd.com/win | iex` works.
- The same pattern is used for `m365/index.html`, but its launcher downloads and verifies `M365-Toolkit.ps1` before running it.
- Files in `tests/Sync-*.ps1` are build scripts despite living under `tests/`.
- Never hand-edit a generated `index.html`. Run the appropriate sync script instead.

```text
.

├── ARCHITECTURE.md                   # this guide
├── win/
│   ├── Windows-Toolkit.ps1           # Windows source, assembler target, release
│   ├── index.html                    # generated web copy of the release
│   ├── modules/                      # independently maintained feature blocks
│   └── disk/
│       ├── Disk-Usage.ps1            # standalone disk tool and assembler target
│       ├── MftScanner.cs             # source embedded into Disk-Usage.ps1
│       └── index.html                # generated web copy of Disk-Usage.ps1
├── m365/
│   ├── Launch-M365.ps1               # web launcher; checksum is generated
│   ├── M365-Toolkit.ps1              # downloaded M365 program
│   └── index.html                    # generated copy of the launcher
└── tests/
    ├── Sync-Site.ps1                 # complete build entry point
    ├── Sync-WindowsToolkit.ps1       # orchestrates Windows sync scripts
    ├── Sync-M365.ps1                 # builds the M365 launcher endpoint
    ├── Sync-<Feature>.ps1            # inserts one module into the release
    └── Test-*.ps1                    # focused PowerShell tests
```

`experiments/` contains prototypes. Nothing there is published unless a build script explicitly copies or embeds it.

Current modular blocks cover health, shared menus, network connections/discovery, registry tweaks, startup tasks, system maintenance, cleanup, and Sysinternals Live launchers. Their filenames and marker pairs are the definitive inventory.

## Source of truth: what to edit

| Change | Edit this | Then run |
| --- | --- | --- |
| Existing modular feature | `win/modules/<Feature>.ps1` | `tests/Sync-WindowsToolkit.ps1` |
| Event Log presets/browser | `win/Windows-Toolkit.ps1` | `tests/Sync-WindowsToolkit.ps1` |
| Network check/category or main menu | `win/Windows-Toolkit.ps1` | `tests/Sync-WindowsToolkit.ps1` |
| Standalone disk PowerShell | `win/disk/Disk-Usage.ps1` | `tests/Sync-WindowsToolkit.ps1` |
| MFT scanner implementation | `win/disk/MftScanner.cs` | `tests/Sync-WindowsToolkit.ps1` |
| M365 program | `m365/M365-Toolkit.ps1` | `tests/Sync-M365.ps1` |
| M365 launcher behavior | `m365/Launch-M365.ps1` | `tests/Sync-M365.ps1` |
| Published `win/index.html`, `win/disk/index.html`, or `m365/index.html` | Do not edit directly | Generated by sync |

The modular blocks currently have matching markers in `Windows-Toolkit.ps1`, for example:

```powershell
# BEGIN REGISTRY TWEAKS
# content replaced by Sync-RegistryTweaks.ps1
# END REGISTRY TWEAKS
```

The module file is authoritative inside those markers. A sync overwrites edits made directly inside a marked block. Code outside marked blocks is maintained directly in `Windows-Toolkit.ps1`.

## Windows toolkit runtime

### Startup

`Windows-Toolkit.ps1` accepts these modes:

- No arguments: validate Windows/PowerShell and open `Start-WindowsMenu`.
- `-NoMenu`: define functions but do not start the UI; tests use this.
- `-Check <id>`: run a registered check without the menu.
- `-Target`, `-Port`, and `-DomainController`: supply input to command-line checks.

The entry point at the bottom of the file is intentionally small. Keep function definitions above it so dot-sourcing with `-NoMenu` exposes everything to tests.

### Menu model

There are two common menu styles:

1. Registry-style functions such as `Start-PcRegistryMenu` build their own `New-PcMenuItem` objects and dispatch a `switch` directly.
2. Registered checks use `Get-NetworkChecks`, `Get-AdChecks`, or `Get-NetworkRepairs`. A category in `Get-NetworkCategories` lists action IDs, and `Get-NetworkMenuItems` turns them into numbered menu rows.

A registered action looks like this:

```powershell
[pscustomobject]@{
    Key      = 'example'
    Id       = 'example'
    Name     = 'Example read-only check'
    MinPS    = '5.0'
    Commands = @('Get-Service')
    Admin    = $false
    Action   = { param($target, $port) Get-Service }
}
```

`Get-NetworkAvailability` checks the PowerShell version, required commands, and administrator token both before display and before invocation. This prevents a disabled menu row from being bypassed through `-Check`.

### Safety convention

Use these labels consistently:

- `Check`: read-only inspection.
- `Browse`: read-only interactive inspection.
- `Menu`: another menu.
- `Change`: writes system state and must explain its scope.

Any change should:

1. Show exactly what it will change.
2. Check prerequisites and administrator requirements.
3. Ask for explicit confirmation.
4. Use `SupportsShouldProcess` when practical.
5. Verify the result by reading it back.
6. Provide undo/restore information.
7. Avoid automatic elevation, reboot, or unrelated remediation.

## How to add things

### Add a small read-only tool to an existing category

This is the shortest path for a command or diagnostic.

1. Add a function in `win/Windows-Toolkit.ps1` outside generated markers, or add it to the appropriate existing module.
2. Add one object to `Get-NetworkChecks`.
3. Add its `Id` to the `Checks` array of the desired object in `Get-NetworkCategories`.
4. Add a focused `tests/Test-<Feature>.ps1` test with external commands mocked.
5. Run the build and tests described below.

Example function:

```powershell
function Get-PcExampleStatus {
    Get-Service -Name EventLog -ErrorAction Stop |
        Select-Object Name, Status, StartType
}
```

Example registry entry in `Get-NetworkChecks`:

```powershell
[pscustomobject]@{
    Key='example'; Id='example'; Name='Example service status'
    MinPS='5.0'; Commands=@('Get-Service'); Admin=$false
    Action={ param($target,$port) Get-PcExampleStatus }
}
```

Then add `'example'` to a category's `Checks=@(...)` list. IDs must be unique and every registered action should be reachable from a category; `Test-NetworkMenus.ps1` checks this.

### Add an Event Log shortcut

Event presets are the objects returned by `Get-PcEventLogChoices` in `win/Windows-Toolkit.ps1`:

```powershell
[pscustomobject]@{
    Name='Example component'
    Log='Microsoft-Windows-Example/Operational'
    Purpose='What this log helps diagnose'
    Directories=@('client','automation')
}
```

`Directories` controls where the shortcut appears. Use one or more IDs returned by `Get-PcEventLogDirectories`: `client`, `server`, `automation`, or `security`.

Use the exact channel name shown by:

```powershell
Get-WinEvent -ListLog *Example* |
    Select-Object LogName, IsEnabled, RecordCount
```

The menu checks whether the channel exists and is enabled; it does not enable logging. After adding the object:

1. Add the expected channel to `tests/Test-EventLogMenu.ps1`.
2. Run `tests/Sync-WindowsToolkit.ps1`.
3. Run `tests/Test-EventLogMenu.ps1` and `tests/Test-EventPreviews.ps1`.

For a shortcut inside another category, register an action that calls:

```powershell
Start-PcEventBrowser 'Microsoft-Windows-Example/Operational'
```

### Add a registry tweak

Registry code lives in `win/modules/Registry-Tweaks.ps1`. The current implementation has hard-coded tweak IDs for Outlook, the RDP client warning dialog, the RDP client transport, and the RDP Session Host transport. Adding another tweak means updating all places whose `ValidateSet` or `switch` enumerates those IDs and placing it under the appropriate end-user device or server menu.

For every tweak, record:

- Display name and stable ID.
- PowerShell provider path such as `HKCU:\Software\...`.
- `.reg` path such as `HKEY_CURRENT_USER\Software\...`.
- Value names, registry types, and exact enabled/reset behavior.
- Whether it is per-user or machine-wide.
- Whether administrator access is required.
- Conflicting policy paths or application state that make the change unsafe.

Follow the existing transaction:

```text
inspect current types/values
        ↓
show proposed change and warnings
        ↓
ShouldProcess + explicit y/N prompt
        ↓
write a .reg undo file under LocalAppData
        ↓
apply with ErrorAction Stop
        ↓
read back and compare
```

Do not silently turn reset into a guessed default. Reset should normally remove the override so Windows or policy supplies its default. Test the module directly in `tests/Test-RegistryTweaks.ps1`; its registry and process operations are mocked, so CI does not change a real registry.

### Add a new top-level feature module

Use a module when a feature is large enough to maintain separately.

1. Create `win/modules/Example-Feature.ps1` containing function definitions only. Do not start the menu at file load time.
2. Choose unique markers and insert them in `win/Windows-Toolkit.ps1` before the final entry-point code:

   ```powershell
   # BEGIN EXAMPLE FEATURE
   # END EXAMPLE FEATURE
   ```

3. Copy an existing `tests/Sync-<Feature>.ps1` to `tests/Sync-ExampleFeature.ps1` and change:

   - module filename;
   - begin/end markers;
   - marker error message.

4. Add `Sync-ExampleFeature.ps1` to `$syncScripts` in `tests/Sync-WindowsToolkit.ps1`.
5. Add the menu function to `Start-WindowsMenu`, or register its actions and category.
6. Add `tests/Test-ExampleFeature.ps1`.
7. Run a full sync twice. The second run should make no changes; this is an idempotence check.

The sync script should replace only text between its unique markers, preserve UTF-8 without a BOM, and copy the assembled launcher to `win/index.html`.

### Add a standalone downloadable script or tool

Choose a permanent URL below `win/`, for example `win/example/`.

Recommended layout:

```text
win/example/
├── Example.ps1       # source
├── README.md         # requirements, safety, use, limitations
└── index.html        # generated byte-for-byte endpoint
```

Add `tests/Sync-Example.ps1` to parse/assemble the source, copy it to the endpoint, and compare SHA-256 hashes. Call that sync script from `Sync-WindowsToolkit.ps1`. If the main toolkit downloads a binary or archive:

- pin a version and SHA-256;
- use HTTPS;
- download to a toolkit-owned temporary directory;
- verify before executing;
- reject hash/version mismatches;
- clean up only paths proven to belong to the toolkit;
- show the download and privilege requirements in the menu.

### Add a main-menu section

In `Start-WindowsMenu`:

1. Add a `New-PcMenuItem` with an unused key.
2. Add the same key to the `switch` and call the section's start function.
3. Update `win/README.md`.
4. Update or add menu reachability tests.

Keep numbering stable when possible; users may build habits or documentation around it.

## The build in detail

### Windows build

`tests/Sync-WindowsToolkit.ps1` runs feature sync scripts in a fixed order.

- `Sync-DiskMft.ps1` embeds `MftScanner.cs` between C# markers in `Disk-Usage.ps1`, then creates `win/disk/index.html`.
- Each feature sync script replaces one marked block in `Windows-Toolkit.ps1` from its module.
- Each sync also copies the current assembled launcher to `win/index.html`; the final copy contains all preceding replacements.
- The orchestrator compares SHA-256 hashes of both published endpoints with their source files and fails on a mismatch.

Because the build writes assembled content back into `Windows-Toolkit.ps1`, running it can legitimately modify tracked files. Review the diff before committing.

### M365 build

`tests/Sync-M365.ps1`:

1. Parses `M365-Toolkit.ps1`.
2. Calculates its SHA-256.
3. Replaces the single `$expectedHash` value in `Launch-M365.ps1`.
4. Parses the updated launcher.
5. Copies it to `m365/index.html`.
6. Verifies the launcher and endpoint hashes match.

At runtime the launcher downloads `M365-Toolkit.ps1` from the same site, verifies that generated checksum, and only then runs the local downloaded file.

## GitHub Actions, line by line

The only workflow is `.github/workflows/build-site.yml`.

### Triggers

| Event | Build? | Deploy? |
| --- | --- | --- |
| Push to any branch | Yes | Only when the ref is `main` |
| Pull request | Yes | No |
| Merge queue (`merge_group`) | Yes | No |
| Manual `workflow_dispatch` | Yes | Only if run on `main` |

This lets proposed changes prove that the site assembles without publishing them.

### `build` job

The build job runs on a fresh Ubuntu runner:

1. `actions/checkout@v4` checks out the commit.
2. PowerShell runs `./tests/Sync-Site.ps1`, which builds Windows and M365 endpoints.
3. PowerShell runs `./tests/Test-RegistryTweaks.ps1` with `LOCALAPPDATA` redirected to the runner's temporary directory.
4. PowerShell runs `./tests/Test-M365MenuEngine.ps1`.
5. PowerShell runs `./tests/Test-SysinternalsLauncher.ps1`.
6. `actions/upload-pages-artifact@v3` uploads the repository working tree (`path: .`) after generation as the Pages artifact.

Important: the current workflow does **not** run every `Test-*.ps1` file. A green Actions result proves the endpoints assembled and the three CI-safe module tests passed; it does not prove the complete Windows-only suite passed.

The build job has only `contents: read`, so it cannot push generated files back to the repository.

### `deploy` job

The deploy job:

- waits for `build` through `needs: build`;
- runs only for `main`, excluding pull requests and merge queue events;
- receives `pages: write` and `id-token: write` only for this job;
- publishes the uploaded artifact with `actions/deploy-pages@v4`;
- reports the final Pages URL through the `github-pages` environment.

Deployment does not run tests again. It publishes exactly the artifact produced by the successful build job.

### Why the endpoint is named `index.html`

GitHub Pages serves a directory's `index.html` at the directory URL. The content does not have to be HTML for `Invoke-RestMethod`; here it is raw PowerShell. That gives the short `/win` and `/m365/` commands while retaining ordinary static hosting.

`CNAME` connects the Pages site to `tools.d0xd.com`, and `.nojekyll` prevents Jekyll from transforming or excluding static content.

## Local maintenance workflow

From the repository root in PowerShell:

```powershell
# 1. Edit the authoritative source/module.

# 2. Assemble every published endpoint.
pwsh -NoProfile -File ./tests/Sync-Site.ps1

# 3. Review exactly what generation changed.
git status --short
git diff --check
git diff

# 4. Run focused tests for the edited area, for example:
pwsh -NoProfile -File ./tests/Test-EventLogMenu.ps1
pwsh -NoProfile -File ./tests/Test-RegistryTweaks.ps1
pwsh -NoProfile -File ./tests/Test-NetworkMenus.ps1
pwsh -NoProfile -File ./tests/Test-WindowsToolkit.ps1
```

Use Windows PowerShell 5.1 as well as PowerShell 7 when changing shared Windows code:

```powershell
powershell.exe -NoProfile -File .\tests\Test-WindowsToolkit.ps1
pwsh.exe       -NoProfile -File .\tests\Test-WindowsToolkit.ps1
```

Tests named `*Live*`, performance measurements, and scripts that require elevation are intentionally specialist/manual checks. Read their parameters and comments before running them.

Before pushing:

- The second `Sync-Site.ps1` run produces no new diff.
- Generated endpoint hashes match their sources.
- PowerShell 5.1-compatible syntax is used where the toolkit promises 5.0+ support.
- New system-changing behavior has confirmation, verification, and undo guidance.
- External commands are mocked in automated tests.
- `win/README.md` or `m365/README.md` describes the user-visible feature.
- No reports, credentials, local paths, or investigation data are staged.

After pushing, open the Actions run named **Build and deploy tool site**. For a `main` push, verify both the `build` and `deploy` jobs. For a pull request, only `build` is expected.

## Troubleshooting

### My module edit disappeared

You probably edited inside a generated marker in `Windows-Toolkit.ps1`. Make the change in the matching `win/modules/*.ps1` file and sync again.

### My web command still runs old code

Check, in order:

1. The authoritative source was edited.
2. `Sync-Site.ps1` updated the matching `index.html`.
3. The generated file was included in the commit, if you keep generated files committed.
4. The Actions `build` job passed.
5. The `deploy` job ran on `main` and passed.
6. You are testing the intended custom-domain URL.

### The build says markers are missing

The begin/end strings in the sync script must exactly match one unique pair in `Windows-Toolkit.ps1`. Restore or correct the markers; do not weaken the check.

### The M365 checksum check fails

Run `tests/Sync-M365.ps1` after editing either M365 file. It expects exactly one 64-hex-character `$expectedHash` assignment in the launcher.

### A feature works locally but not in Actions

The build runner is Ubuntu. Assembly and mocked tests must not call Windows-only commands at file-load time. Put Windows calls inside functions/actions and test them with mocks. Runtime-only Windows behavior should be validated separately on Windows.

## Sensible future improvements

The current design is deliberately simple, but these changes would lower maintenance cost further:

1. Add a `Test-All.ps1` orchestrator that declares which tests are safe for CI, then call it from the workflow.
2. Replace one-sync-script-per-module duplication with a data table of module filename and marker pair.
3. Move Event Log preset data and simple check metadata into `.psd1` files once the schemas stabilize.
4. Add an idempotence CI step that runs `Sync-Site.ps1` twice and fails if the second run changes hashes.
5. Upload only explicit public site paths if repository-internal files should not be part of the Pages artifact.

Make those as separate, tested changes. The present architecture works without them, and this guide describes the code as it exists now.
